# Metrics by service

Use one `cloudwatch.GetMetricData` call per resource containing all its metrics. For latency metrics request `p50`, `p90` and `p99` as extended statistics. Counts use `Sum`. Saturation gauges use `Maximum` (or `Minimum` where low is bad).

## Elastic Load Balancing

### Application Load Balancer (namespace `AWS/ApplicationELB`, dimensions `LoadBalancer`, optionally `TargetGroup`)

| Metric | Statistic | Use |
|---|---|---|
| TargetResponseTime | p50, p90, p99 | Time from request sent to target until response headers received. Latency of the targets, not the load balancer. |
| RequestCount | Sum | Rate |
| HTTPCode_Target_5XX_Count | Sum | Target errors |
| HTTPCode_ELB_5XX_Count | Sum | Errors generated by the load balancer itself |
| RejectedConnectionCount | Sum | Load balancer reached its connection limit |
| TargetConnectionErrorCount | Sum | Load balancer could not connect to targets |
| HealthyHostCount, UnHealthyHostCount | Minimum, Maximum | Capacity behind the load balancer (use `TargetGroup` dimension) |

### Network Load Balancer (namespace `AWS/NetworkELB`)

| Metric | Statistic | Use |
|---|---|---|
| ActiveFlowCount, NewFlowCount | Maximum, Sum | Rate and concurrency |
| TCP_Target_Reset_Count, TCP_ELB_Reset_Count | Sum | Connection resets |
| UnHealthyHostCount | Maximum | Capacity |

## Amazon API Gateway (namespace `AWS/ApiGateway`)

## Amazon EBS (namespace `AWS/EBS`, dimension `VolumeId`)

| Metric | Statistic | Use |
|---|---|---|
| VolumeReadOps, VolumeWriteOps | Sum | Divide by period seconds for IOPS; compare with provisioned or baseline IOPS |
| VolumeReadBytes, VolumeWriteBytes | Sum | Throughput; compare with the volume type limit |
| VolumeQueueLength | Average, Maximum | Saturation |
| BurstBalance | Minimum | gp2, st1 and sc1 burst saturation |

## Amazon ECS (namespace `AWS/ECS`, dimensions `ClusterName`, `ServiceName`)

| Metric | Statistic | Use |
|---|---|---|
| CPUUtilization, MemoryUtilization | Average, Maximum | Utilization against the service's reserved CPU and memory |

With Container Insights enabled (namespace `ECS/ContainerInsights`): `RunningTaskCount`, `DesiredTaskCount`, `CpuUtilized` (CPU units), `CpuReserved` (CPU units), `MemoryUtilized` (MB), `MemoryReserved` (MB). A gap between desired and running tasks during the window is a scaling or placement problem.

Warning: `CpuUtilized` and `MemoryUtilized` are absolute amounts (CPU units and megabytes), not percentages. Compute utilization as `CpuUtilized` / `CpuReserved` and `MemoryUtilized` / `MemoryReserved`, or use `AWS/ECS` `MemoryUtilization` and `CPUUtilization` which are already percentages.

## Amazon EKS

With Container Insights enabled (namespace `ContainerInsights`, dimensions `ClusterName`, `Namespace`, `PodName` or `Service`): `pod_cpu_utilization`, `pod_memory_utilization`, `pod_cpu_utilization_over_pod_limit`, `pod_number_of_container_restarts`, `node_cpu_utilization`, `node_memory_utilization`. Without Container Insights, report pod-level resource use as unmeasured.

## CloudWatch Application Signals (namespace `ApplicationSignals`)

Per service and operation: `Latency` (p50, p90, p99), `Fault`, `Error`. Use `application-signals.ListServiceDependencies` for per-dependency latency. If an SLO exists, `application-signals.ListServiceLevelObjectives` and `GetServiceLevelObjective` give the target and attainment.

## AWS X-Ray

- `xray.GetServiceGraph` for the window: nodes, edges, and response time histograms per edge.
- `xray.GetTraceSummaries` filtered by `responsetime > N` or by `service("name")` to sample slow traces, then `xray.BatchGetTraces` for up to a handful of trace IDs to see which subsegment holds the time.

## Amazon EC2 Auto Scaling (namespace `AWS/AutoScaling`, dimension `AutoScalingGroupName`)

Group metrics must be enabled on the group to publish.

| Metric | Statistic | Use |
|---|---|---|
| GroupInServiceInstances | Maximum | Instances currently serving; compare with `GroupMaxSize` to see a group pinned at its maximum |
| GroupDesiredCapacity, GroupMaxSize, GroupMinSize | Maximum | Scaling envelope; desired at max means no room to scale out |
| GroupTotalInstances, GroupPendingInstances, GroupTerminatingInstances | Maximum | Launch and replacement activity during the window |

Read min, max and desired with `autoscaling:DescribeAutoScalingGroups` and the last action with `autoscaling:DescribeScalingActivities`.

## Service quotas and usage (namespace `AWS/Usage`)

`AWS/Usage` publishes current usage for many quotas (dimensions `Type`, `Resource`, `Service`, `Class`), charted against the applied quota from `servicequotas:GetServiceQuota` / `ListServiceQuotas`. Which quotas publish here is to verify against "AWS usage metrics". Usage near the quota with throttle errors in client logs is a hidden-limit finding, not resource saturation.

## Breaking metrics down by dimension

The aggregate hides a degraded slice; read key metrics broken down before trusting the total.

- **ALB per Availability Zone.** `AWS/ApplicationELB` metrics support an `AvailabilityZone` dimension; split `TargetResponseTime`, `HTTPCode_Target_5XX_Count` and `RequestCount` by AZ to find a single degraded zone.
- **CloudWatch Contributor Insights.** Rules over logs or metrics surface the top-N contributors (the hottest key, the noisiest caller, the slowest host). Read a rule report with `cloudwatch:GetInsightRuleReport`.
- **CloudWatch Metrics Insights.** A SQL-like query engine over metrics; a `GROUP BY` query (for example group latency or errors by `InstanceId`, `Operation` or `AvailabilityZone`) returns per-member series in one call to compare members against peers.

## Client-side views (Synthetics and RUM)

- **CloudWatch Synthetics canaries** run scripted requests on a schedule and measure latency and availability from outside the service, independent of server metrics; useful to detect a gray failure the server does not see.
- **CloudWatch RUM** captures real-user browser and mobile performance (page load, core web vitals, errors). Both give the customer-perspective number that server-side metrics miss.

Verify metric names and dimensions against the CloudWatch metrics documentation for each service before relying on a value that drives a severity rating.

## Deep checks by service (Step 5)

Run only the checks that apply to the suspect hop.

- **Databases (RDS, Aurora).** If Performance Insights is enabled, call `pi.GetResourceMetrics` with `db.load.avg` grouped by `db.wait_event` and by `db.sql_tokenized`, then `pi.DescribeDimensionKeys` for the top statements. Compare `db.load.avg` with the instance vCPU count. Check connections against the configured maximum, replica lag and storage throughput limits. If the top-statement call fails, apply the failed-call rule in `diagnosis-rules.md` and fall back to trace data (SQL spans or database segments); keep the cause Likely until the statement is read from either source.
- **Lambda.** Read `MemorySize` and `Timeout` with `lambda:GetFunctionConfiguration`, reserved concurrency with `lambda:GetFunctionConcurrency`, and provisioned concurrency with `lambda:ListProvisionedConcurrencyConfigs`. If the configuration read fails, take the memory size from the `Memory Size` field of the `REPORT` log lines, which also carry `Duration`, `Billed Duration`, `Max Memory Used` and `Init Duration`. Compare Duration p50 and p99 with the timeout. When p99 nears the timeout, treat memory as the CPU setting (see `hidden-limits.md`, Lambda memory sets CPU share) and apply the Lambda magnitude check and the cold-start check in `diagnosis-rules.md`. Low `Max Memory Used` is not headroom on a CPU-bound function. Check `ConcurrentExecutions` and `Throttles` against reserved and account concurrency.
- **Other compute (EC2, ECS, EKS).** Scaling configuration against observed demand: Auto Scaling group min, max and desired over the window, scaling activities, target tracking targets, ECS desired versus running count.
- **Caches and NoSQL.** Confirm the cache exists in configuration or code first. Then ElastiCache hit ratio, evictions and engine CPU; DynamoDB throttled requests per table and per index, and on-demand or provisioned capacity mode.
- **Queues and streams.** Age of the oldest message or iterator age against the processing SLA; backlog against arrival and completion rate; catch-up rate and drain time during recovery; whether consumers scale with backlog; per-consumer throughput; visibility timeout and long polling, and whether a slow consumer holds messages in flight (see `hidden-limits.md`). For an event source mapping, compare effective concurrency (completion rate x duration) with its maximum concurrency and with the function's reserved concurrency.
- **Callers and retries.** Read client timeout and retry settings from the caller's configuration or environment. Compare the timeout with the dependency's p99 at single-attempt load (a busy-window p99 can be inflated by retries) and with the caller's own deadline, count attempts received against requests originated, and apply the magnitude test (see `diagnosis-rules.md`, Retry amplification).
- **Network path.** Cross-AZ calls on the hot path, NAT gateway port allocation errors and dropped packets, load balancer rejected connections.
