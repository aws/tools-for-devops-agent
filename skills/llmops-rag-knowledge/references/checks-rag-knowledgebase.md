# Checks — Knowledge Bases / RAG (LLM-KB)

Covers Amazon Bedrock Knowledge Bases (retrieval-augmented generation).

Each row: `check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation`

Family code: **KB** = knowledge bases / RAG. Family prefix: `LLM-KB-`.

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. Thresholds without an AWS-published value are marked `workload-specific` at severity INFO. No check in this family is CRITICAL. The exact calls and fields for each rule are in `rag-review-playbook.md`.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-KB-001 | Operational Excellence | HIGH | `ListIngestionJobs` for the data source (sorted `STARTED_AT` `DESCENDING`, all pages) returns empty, or no `COMPLETE` job ever reported `numberOfNewDocumentsIndexed` > 0 — the vector store is empty and retrieval returns nothing. A later no-change sync (0 new, 0 modified) does not count as empty. | Run `aws bedrock-agent start-ingestion-job --knowledge-base-id <kb-id> --data-source-id <ds-id>` for each data source; confirm a `COMPLETE` job with `numberOfNewDocumentsIndexed` > 0. | https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-sync-ingest.html |
| LLM-KB-002 | Reliability | HIGH | The latest terminal ingestion job (`COMPLETE` / `FAILED` / `STOPPED`) is `FAILED` or `STOPPED`, or its statistics show `numberOfDocumentsFailed` > 0 — content is stale or partially missing. | Read `failureReasons` from `GetIngestionJob` (and the KB's `APPLICATION_LOGS` if delivered), fix source permissions/format/size issues, and re-run the ingestion job until `COMPLETE` with zero failures. | https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-sync-ingest.html |
| LLM-KB-003 | Performance | INFO | Chunking strategy may not fit the documents. `chunkingConfiguration` absent means the service default (about 300 tokens, sentence boundaries preserved); `NONE` means one chunk per document. Judge fit against observed document sizes and structure. Threshold `workload-specific`. | If the documents are long and structured, choose fixed-size, hierarchical or semantic chunking. The strategy cannot be changed on an existing data source: create a new data source with the new `chunkingConfiguration` and sync it. | https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-customize-ingestion.html |
| LLM-KB-004 | Performance | MEDIUM | `GetKnowledgeBase` `embeddingModelArn` names a model whose `GetFoundationModel` `modelLifecycle.status` is `LEGACY`, or that is no longer on the supported-embedding-models page. Never fires on `amazon.titan-embed-text-v2:0` or `cohere.embed-*-v3`; an `ACTIVE` `amazon.titan-embed-text-v1` is an INFO note that a newer Titan generation exists. | Plan a migration to a supported current embedding model; this requires a new vector index, re-embedding all content and re-evaluating retrieval quality. | https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-supported.html |
| LLM-KB-005 | Security | HIGH | No customer managed KMS key protects the data source: `GetDataSource` `serverSideEncryptionConfiguration` is absent (transient ingestion storage then uses an AWS-owned key) and the source bucket's default encryption (`GetBucketEncryption`) is SSE-S3 or SSE-KMS with an AWS managed key. Report the state as "AWS-owned key / SSE-S3, not a CMK", never "unencrypted". | Set `serverSideEncryptionConfiguration.kmsKeyArn` to a customer managed key on the data source and set SSE-KMS with that key as the bucket default; grant the KB service role `kms:GenerateDataKey` and `kms:Decrypt`. | https://docs.aws.amazon.com/bedrock/latest/userguide/encryption-kb.html |
| LLM-KB-006 | Security | HIGH | The vector store is encrypted with an AWS-owned key rather than a CMK, and/or is reachable from the internet. For OpenSearch Serverless: `BatchGetCollection` `kmsKeyArn` `auto` or encryption policy `AWSOwnedKey: true`; network policy (`GetSecurityPolicy --type network`) with `AllowFromPublic: true` on a `collection` rule. For RDS / OpenSearch managed clusters read `StorageEncrypted`/`KmsKeyId`/`PubliclyAccessible` or `EncryptionAtRestOptions`/`VPCOptions`. Third-party stores are not checkable from AWS APIs and are disclosed, not raised. | Restrict the network policy to `SourceVPCEs` or `SourceServices` `bedrock.amazonaws.com` with `AllowFromPublic: false` (`aws opensearchserverless update-security-policy --type network …`). An AOSS collection's key cannot change after creation: for a CMK, create a new collection under a CMK encryption policy and re-sync. | https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-network.html |
| LLM-KB-007 | Performance | INFO | The corpus has many exact-match terms (codes, IDs, SKUs), the vector store supports hybrid search (Amazon RDS, OpenSearch Serverless or MongoDB with a filterable text field), and the application's use of `overrideSearchType` is unconfirmed. The search type is a per-request `Retrieve` / `RetrieveAndGenerate` parameter and is not stored on the KB, so it cannot be read from configuration. Threshold `workload-specific`. | Where supported, test `retrievalConfiguration.vectorSearchConfiguration.overrideSearchType = HYBRID` on representative exact-match queries and adopt it in the application if results improve. | https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html |
| LLM-KB-008 | Operational Excellence | LOW | No agent references the KB: `ListAgents` → `ListAgentVersions` → `ListAgentKnowledgeBases` (every version) finds no attachment. Application use of `Retrieve` / `RetrieveAndGenerate` is visible only in CloudTrail data events for `AWS::Bedrock::KnowledgeBase`; if none are recorded, report application use as unverified, never a flat "orphaned". | Confirm the owning application; enable CloudTrail data events for the KB to see callers. Attach the KB to its agent if one should use it. Decommission only after callers are confirmed absent. | https://docs.aws.amazon.com/bedrock/latest/userguide/logging-using-cloudtrail.html |
| LLM-KB-009 | Quality & Evaluation | MEDIUM | No Bedrock evaluation job with `applicationType` `RagEvaluation` whose `ragIdentifiers` include this KB exists — retrieval relevance is unmeasured. A `ModelEvaluation` job does not count. Guardrail contextual-grounding settings are not a retrieval evaluation. | Hand off to llmops-quality-evaluation to run a retrieve-only or retrieve-and-generate RAG evaluation job against the KB and track the scores over time. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html |
| LLM-KB-010 | Operational Excellence | INFO | Data source sync appears purely manual for a corpus that changes, from a named signal: `StartIngestionJob` CloudTrail events only from IAM users or console sessions, and no EventBridge Scheduler schedule or EventBridge rule that starts ingestion. If no signal can be read, report "unconfirmed" and name the missing signal. Threshold `workload-specific`. | Automate ingestion on a schedule or on source-change events (for example an EventBridge Scheduler schedule or an S3 event → Lambda → `StartIngestionJob`). | https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-sync-ingest.html |
| LLM-KB-011 | Security | HIGH | An ingestion job or a `Retrieve`/`RetrieveAndGenerate` call fails (or would fail) for a permissions reason, not a data reason. Read-only detection: `iam:SimulatePrincipalPolicy` on the KB / data-source execution role for `s3:GetObject` + `s3:ListBucket` on the data-source prefix, `kms:Decrypt` on the data-source / vector-store CMK; inspect the role trust policy for a `bedrock.amazonaws.com` principal; `s3:GetBucketPolicy` for a cross-account bucket-policy deny; `organizations:ListPoliciesForTarget` + `DescribePolicy` for an SCP explicit deny. An `AccessDenied`/`AccessDeniedException` on ingestion or retrieval with the data itself intact is the signal. | Name the specific missing grant and return the exact statement to add — e.g. an `s3:GetObject`/`s3:ListBucket` statement scoped to the data-source bucket/prefix, a `kms:Decrypt` grant on the named CMK, a trust-policy statement allowing `bedrock.amazonaws.com` to assume the role, or the cross-account bucket-policy / SCP statement that must be amended. Recommend only — never attach or put a policy. Mask the account segment of every ARN quoted as evidence and never echo secret-shaped condition values. | https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup.html |
| LLM-KB-012 | Reliability | MEDIUM | Ingestion is slow/failing or `Retrieve` calls are throttled because an embedding-model invocation quota or a knowledge-base / Retrieve request-rate quota is being hit, or there is no burst headroom. Read-only detection: `servicequotas:GetServiceQuota` (service-code `bedrock`) for the relevant embedding-model invocation and knowledge-base / Retrieve request-rate quotas, correlated with CloudWatch throttle/usage over a window (`InvocationThrottles` on the embedding model, `EstimatedTPMQuotaUsage`, or retrieval-path throttling). MEDIUM only when the window shows sustained throttles against a quota value read from the account; headroom alone, with no throttles, is `INFO` because AWS publishes no threshold — do not invent one. | Identify the specific quota being approached/hit and recommend requesting an increase for that exact quota (`aws service-quotas request-service-quota-increase --service-code bedrock --quota-code <code> --desired-value <n>`), batching/backing off ingestion, or spreading Retrieve load — recommend only, never request the increase from the skill. Report the quota value and the throttle count as observed; do not promote a headroom-only signal to a hard failure. | https://docs.aws.amazon.com/bedrock/latest/userguide/quotas.html |
