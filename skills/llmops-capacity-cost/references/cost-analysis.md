# Cost Analysis

Billed-vs-estimated cost methodology and cost-optimization checks for Bedrock + SageMaker GenAI workloads. This file carries the **COST** and **PT** (provisioned throughput) family checks.

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. Severity comes from each catalog row. A `workload-specific` threshold has no AWS-published value: name it as such next to the observed value, set it from observed usage, and keep the row's severity.

---

## 1. Cost methodology — billed first, token model second

Bedrock bills **four token types**, each at its own unit price: input, output, cache read, cache write. Unit prices also differ by **service tier** (Standard, Flex, Priority — where published) and by **routing** (in-region vs `cross-region-global`). Summing only input and output tokens at one rate per model is the most common cause of totals that do not match the bill. Sources: https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-understanding-cur-data.html, https://aws.amazon.com/bedrock/pricing/

**1a. Billed spend (Cost Explorer = billed truth).** Label these figures `(billed)`.
1. **Per model:** `aws ce get-cost-and-usage --group-by Type=PRODUCT_ATTRIBUTE,Key=model --metrics UnblendedCost UsageQuantity` (also `provider`, `inferenceType`, `feature`). Results come back keyed by display name (`model$Claude Sonnet 5`, `model$Nova Lite`); `model$` holds costs with no model. With `GroupBy`, each period's `Total` is empty (`{}`): read the `Groups`, never take the empty `Total` as $0; a period with no `Groups` has no billed spend in that grouping. `Type=DIMENSION,Key=model` fails with `ValidationException`; product-attribute filters and `--dimension-key` are rejected by current CLI/SDK builds, so group rather than filter. Product-attribute data starts at a fixed date. A window that begins earlier fails with `DataUnavailableException`. Don't assume the date: on that error, regroup the same window by `USAGE_TYPE` and say so. API: https://docs.aws.amazon.com/aws-cost-management/latest/APIReference/API_GetCostAndUsage.html
2. **Per usage type** (any period): group by `USAGE_TYPE`. Lines encode model, token type, tier and routing, but naming varies — e.g. `USE1-NovaLite-input-tokens` vs `USE1-anthropic.claude-sonnet-5-mantle-input-tokens-standard` — so match a model's lines loosely. `UsageQuantity` is often in thousands of tokens. Provisioned Throughput bills as model-unit hours, not tokens.
3. **Guardrail spend** bills as `USE1-Guardrail-*` usage types and appears in the `model$` product-attribute group. Label it as Guardrail cost and route Guardrail posture to `llmops-guardrails`.
4. **Service name:** do not filter on `SERVICE = "Amazon Bedrock"`. Bedrock costs can appear under more than one service name, so a single-name filter undercounts (`api-quirks.md` §16). Omit the SERVICE filter with product attributes, or list names with `ce:GetDimensionValues` (`Dimension = SERVICE`, `SearchString = Bedrock`).
5. **Per caller / per application:** billed only with IAM principal attribution (CUR 2.0), application inference profiles, or project tags, each with cost allocation tags activated (allow up to 24 h to populate). Source: https://docs.aws.amazon.com/bedrock/latest/userguide/cost-management.html Before saying no billed per-team split exists, list application inference profiles (`bedrock:ListInferenceProfiles`, `typeEquals=APPLICATION`) and their tags, and name any you find. Only the management (payer) account of an organization, or a standalone account, can view and activate cost allocation tags (https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/custom-tags.html): `AccessDenied` on `ce:ListCostAllocationTags` from a member account is expected, not a permission to add; say the management account activates the tag key. A new key can take up to 24 hours to appear for activation and up to 24 hours more to activate (https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/activating-tags.html); the management account can backfill activation for up to 12 months (https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-allocation-backfill.html), never before the resource was tagged.

**1b. Token model (cross-check and fallback).** Label these figures `(estimated)`.
1. Pull `InputTokenCount`, `OutputTokenCount`, `CacheReadInputTokenCount`, `CacheWriteInputTokenCount` (Sum) from `AWS/Bedrock`, by `ModelId`, over the window.
2. Multiply each token type by its rate. Rate sources, in order: prices the user supplied (say so); `pricing:GetProducts`; the Bedrock pricing page (https://aws.amazon.com/bedrock/pricing/) read with `verify_aws_claim`. `pricing:GetProducts` is an AWS API call, not a docs verification, so it doesn't use up `verify_aws_claim`'s single read; the overview page often lacks per-model rates, so don't spend that read on one model's page per model. `GetProducts` (us-east-1 endpoint, one call per model): service code `AmazonBedrockFoundationModels` for third-party models or `AmazonBedrock` for Amazon models, filter `regionCode` plus `model` with the Pricing name (`Claude Sonnet 5`, `Nova Lite`, `Nova 2.0 Lite`) or, for Titan, `titanModel` (`TitanEmbeddingsV2-Text-input`). Read tier and routing from each row's `usagetype` (contains `global` in any case = global; `flex`, `priority`; none = Standard) and skip rows containing `batch`, `custom-model`, `Customization`, `ProvisionedThroughput` or `reserved`. In testing, 5 calls priced all 5 models in use, Claude Sonnet 5 at $2.20/$11 per 1M (Standard), matching the bill. Match the exact model name and version as published (e.g. `Claude Sonnet 4.6`; `Claude Sonnet 5` ≠ `Claude Sonnet 5.5`) and the region. Take the on-demand rate for the assumed tier (Standard, Flex, Priority) and routing (in-region, geographic, global); billed usage types show which apply (`-flex`, `-priority`, `-cross-region-global` / `_global_standard`; none of these = Standard). Billed `-mantle-…-standard` lines bill at the model's Standard rate (verified exact for Claude Sonnet 5). Don't use batch, custom-model, Provisioned Throughput or reserved rates for on-demand tokens. Only published tiers exist (Nova Micro has Standard only). Read each rate's unit (per 1K or per 1M tokens) and record the date the page was read. A rate no source gives = unpriced. Standard and global rates differ; CloudWatch tokens are split by neither, so state the rate you assumed. Never back-derive a rate from the bill for the cross-check — it matches by construction. With no citable price, write "cross-check not computed" with the reason; never drop the cross-check silently. You may still report the billed effective rate per usage-type line (`UnblendedCost` ÷ `UsageQuantity`) as an observation labelled "derived from the bill, not a cross-check". That rate describes only the days it was read from: never apply it to other days, other models or tokens billed at $0, and never use it to size what $0-billed usage "would" cost. If `pricing:GetProducts` is denied (AccessDenied: the managed `AIDevOpsAgentAccessPolicy` does not include it), report the model as "unpriced: pricing:GetProducts denied" and list the permission under scope not covered.
3. Compare CloudWatch token counts with billed `UsageQuantity` **per day** (`--granularity DAILY`, group by `USAGE_TYPE`) for every model with metered tokens, whether or not a price is citable. Report days or models with metered tokens and no billed line as "metered, not billed — unexplained"; check dates before naming a cause. Label a day with fewer billed than metered tokens only from figures read now (your own read, or a re-read on both sides of figures the user pasted, SKILL.md "Pasted figures"): the current UTC day is "not billed yet"; yesterday is "partly billed", because Cost Explorer lags CloudWatch: show both token counts, keep it out of the divergence, and say the billed total is not complete yet (in testing, a day's billed tokens matched CloudWatch through 13:00 UTC; the evening's traffic was still unbilled about 23 hours later). A day 2 or more days old with clearly more metered than billed tokens is "metered above billed — unexplained": give both counts and, before naming a cause, check that the day has stopped billing (a later read no longer changes it), that the metered side isn't double-counted (`ModelId` + `ContextWindow` added to `ModelId`, metrics-and-logs.md) and the window and period (`api-quirks.md` §21–22). In testing, a reported 2.1× gap (9.0M metered vs 4.26M billed input) was a partly billed day plus today's unbilled traffic. Then compare dollars per model and in total against 1a. A match only shows that the two sources agree inside the window. Before calling any figure exact or complete, run the coverage check (SKILL.md Step 3b, `api-quirks.md` §22). `End` is exclusive, so check that no model has billed cost or tokens on days the window leaves out, in particular yesterday and today. If the gap is more than a few percent, report it and itemise the billed lines the model does not cover: PT model-unit hours, `-flex` / `-priority` / `-cross-region-global` lines priced differently from the assumed rate, and non-token features.
4. Use the token model as the result only when 1a is unavailable (Cost Explorer denied, or no data for the window), for per-caller or per-application allocation without billed attribution, and for what-if comparisons. Say which case applies.

Direct any forward-looking price projections to the AWS Pricing Calculator / Bedrock pricing page — do not fabricate future prices.

**Confirmation signals for LLM-COST-001 and LLM-COST-002.** Both checks describe a usage pattern that token totals alone cannot prove. Raise them at catalog severity only when one of these read-only signals confirms the pattern; otherwise raise `INFO (unconfirmed)` and name the missing signal:

- `CacheReadInputTokenCount` / `CacheWriteInputTokenCount` (`AWS/Bedrock`, Sum, by `ModelId`). AWS documents that both are **0 when prompt caching is not used**, and that `InputTokenCount` excludes cached tokens. A *measured* 0 on cache reads confirms LLM-COST-002 only together with either (a) the prefix-hash query (metrics-and-logs.md) showing one prompt prefix on a large share of the model's calls (state the share), or (b) a high input floor: the 10th percentile of `input.inputTokenCount`, not the average, at or above the model's minimum tokens per cache checkpoint (prompt-caching docs). A low floor with a high average means mixed prompt sizes and confirms nothing on its own: raise `INFO (unconfirmed)`. In testing, Claude Sonnet 5 had cache reads 0, a minimum of 12, a 10th percentile of 1,936 and an average of 4,211 input tokens; one prefix hash covered 781 of 2,139 calls, which confirmed it through (a). *No datapoints* is not a 0 — it usually means the metric was not emitted (model may not support caching); report it as such (`api-quirks.md` §15). Confirm the model supports prompt caching before raising.
- **Caching in use but not paying off** (second form of LLM-COST-002): for every model with `CacheWriteInputTokenCount` > 0, compare it with `CacheReadInputTokenCount` (Sum, same window, by `ModelId`). Cache writes are priced above normal input and reads below it, so caching saves money only when each written prefix is read back several times. Writes clearly above reads confirm this form: give both counts and the write:read ratio, and say the saving depends on the model's write and read rates (price them per the token model, or say "not priced"). In testing, GPT-5.6 Terra wrote 4.4M and read 0.57M cache tokens in 14 days (7.7:1). Causes to check, not to assert: prefixes that change between calls, cache TTL shorter than the gap between calls, cache points on content that varies. Run this for every model in a cost review, not only when the user asks about caching.
- Invocation-log content (Logs Insights over the Bedrock log group): a `stopReason` shift toward `max_tokens` **together with** a heavy tail made of those `max_tokens` records (a small share of records carrying a disproportionate share of `outputTokenCount`) confirms LLM-COST-001. Neither of these confirms it: long outputs that stop on `tool_use` or `end_turn` (in testing, 97% of records stopped on `tool_use` and carried 99.7% of output), or a `max_tokens` share with uniformly small outputs (2.4% of records, all capped at 256 tokens). Raise `INFO (unconfirmed)`. Repeated identical prompt prefixes confirm LLM-COST-002.

**Quota link.** Output tokens burn TPM quota at a model-specific burndown rate (5x–15x for current Anthropic and OpenAI models), and `max_tokens` is reserved from the quota up front for every request. An unbounded `maxTokens` therefore drives throttling (LLM-INV-007, LLM-PT-002) as well as cost — say so when both fire together. Source: https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-token-burndown.html

|---|---|---|---|---|---|
| LLM-COST-001 | Cost Optimization | MEDIUM | A small set of invocations drives a disproportionate share of `OutputTokenCount` (long generations) — unbounded `maxTokens`. Confirm only with a `max_tokens` shift **and** a heavy `outputTokenCount` tail made of `max_tokens` records; long `tool_use` / `end_turn` outputs, a low uniform cap, or no log signal raise `INFO (unconfirmed)`. | Cap `maxTokens`, add stop sequences, trim system prompts. Threshold `workload-specific`. | https://docs.aws.amazon.com/bedrock/latest/userguide/inference-parameters.html |
| LLM-COST-002 | Cost Optimization | MEDIUM | `CacheReadInputTokenCount` measured 0 together with a repeated prompt prefix (prefix-hash query) or a high input floor (10th percentile, not the average, at or above the model's minimum cache-checkpoint size) — prompt caching not in use, inflating input-token cost; **or** `CacheWriteInputTokenCount` clearly above `CacheReadInputTokenCount` for a model — caching in use but rarely read back. Otherwise raise `INFO (unconfirmed)`. | Use prompt caching for stable prefixes where the model/API supports it; where writes exceed reads, make the cached prefix byte-identical across calls, match the cache TTL to the call spacing, or turn caching off for that path. Threshold `workload-specific`. | https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html |

## 2. Idle provisioned throughput detection (PT family)

Provisioned Throughput (PT) buys dedicated model units billed hourly for the commitment term, regardless of use. Idle PT is pure waste.

Detection: for each `GetProvisionedModelThroughput`, read `Invocations` and token Sums for the PT per UTC day over the window. Report observed tokens per minute next to the committed `modelUnits`, and the number of days with no datapoints; do not state a utilization % unless the user supplies the per-unit capacity (it varies by model). Raise LLM-PT-001 for an `InService` PT in either case:
- **Idle most of the window:** no datapoints on most days of the window (more than half). The PT bills every hour but carries no recorded traffic on those days; this needs no per-unit capacity. No datapoints on every day = fully idle.
- **Low throughput against a known capacity:** the per-unit capacity is known (user-supplied, or a reserved-TPM commitment below) and observed throughput is far below it. Threshold `workload-specific`.

A PT with traffic on most days and no known per-unit capacity is not raised: report its throughput and say utilization could not be computed.

PT is the **reserved** service tier: it bills per model-unit hour, not per token, and its quota use is computed differently (no output burndown; cache tokens weighted). Some newer models instead reserve input and output **tokens per minute** for 1 or 3 months, billed per 1K TPM-hour whether used or not (usage types like `USE1-Claude4.5Sonnet-reserved-3-month-input-tokens-per-minute-cross-region-global`; rates under pricing service code `AmazonBedrockService`). Treat these like PT for LLM-PT-001/003: reserved TPM = billed `UsageQuantity` × 1,000 ÷ hours in the window, compared with observed input and output tokens per minute. Keep all reserved capacity out of the token model and out of on-demand quota headroom.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-PT-001 | Cost Optimization | HIGH | A Provisioned Throughput commitment (`status = InService`) or a reserved-TPM commitment shows sustained low utilization: no datapoints on most days of the window, or, with a known per-unit capacity, token throughput far below it (see Detection above). | There is no in-place resize (`UpdateProvisionedModelThroughput` changes only the name or model). To right-size, buy a PT with fewer model units, then delete the old one. A no-commitment PT can be deleted at any time; a 1- or 6-month PT can't be deleted before its term ends, and it **renews automatically** at the end of each term, so it does not lapse on its own. Billing continues until the PT is deleted. For an idle commitment: move the traffic to on-demand or an inference profile now, and have the user delete the PT once the term ends (before it renews). Never delete it yourself. Threshold `workload-specific`. | https://docs.aws.amazon.com/bedrock/latest/userguide/prov-throughput.html |
| LLM-PT-002 | Cost Optimization | MEDIUM | On-demand workload is sustained near its throttle ceiling (persistent `InvocationThrottles` or quota rejections) and would be cheaper/more reliable on PT, but no PT is provisioned. | Evaluate a Provisioned Throughput commitment for the steady baseline; keep on-demand/inference-profile for burst. | https://docs.aws.amazon.com/bedrock/latest/userguide/prov-throughput.html |
| LLM-PT-003 | Reliability | MEDIUM | PT provisioned against a model version nearing or past end of life — commitment may outlive the model. | Align PT commitment term with the model lifecycle; plan migration before end-of-life (ties to LLM-INV-003). | https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html |

## 3. Batch vs on-demand cost comparison

Bedrock **Batch inference** is offered at a discount versus on-demand for the same model, for latency-tolerant bulk jobs.

Procedure: identify high-volume, non-interactive invocation patterns (nightly summarization, bulk classification). Estimate on-demand token cost (section 1) and compare against the batch rate on the pricing page. If latency tolerance allows, batch wins.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |

| LLM-COST-003 | Cost Optimization | MEDIUM | Large latency-tolerant jobs run on-demand instead of batch (ties to LLM-INV-009). | Move to `CreateModelInvocationJob` (batch) for the discounted rate. | https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html |

## 5. Cross-region inference cost implications

Cross-region (system-defined) inference profiles route requests across regions for resilience/capacity. Two kinds bill differently:

- **Geographic profiles** (`us.`, `eu.`, `apac.`, `jp.`, `au.` and every other prefix except `global.`): tokens are charged at the **source region's** rate.
- **Global profiles** (`global.`): tokens bill under their own usage type with **its own unit price**, which differs from the in-region rate and can be lower or higher (in testing, lower for Claude Sonnet 5). Spellings vary (`-cross-region-global`, `_global_standard`, …): match any usage type containing `global`, in any case (https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-understanding-cur-data.html).

Read the actual rate from the billed usage-type line in Cost Explorer or from the pricing page. If the profile's tokens are metered but not billed yet, there is no line: use the pricing-page rate, label the figure `(estimated)` and report the days as "metered, not billed" (§1b). Never quote a difference between profile kinds without that citation. Data-transfer treatment is not documented as zero; say it must be confirmed rather than asserting there is none.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-COST-005 | Cost Optimization | INFO | Cross-region inference profile in use without confirming its billed rate (source-region rate for geographic profiles; a usage type containing `global` for global profiles) and data-transfer treatment. Threshold `workload-specific`. | Read the profile's billed usage-type line in Cost Explorer or the pricing page, confirm data-transfer treatment, and document the expected cost. | https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html |

## 7. Invocation-log retention cost

Model invocation logging writes prompts, completions and metadata to a CloudWatch log group and/or S3 prefix. With no retention or lifecycle policy, stored volume, and its cost, grows without bound. Full text, image and embedding data delivery multiplies the volume. The logging configuration itself is owned by `llmops-bedrock-configuration`; this check covers only the cost consequence.

Detection: `logs:DescribeLogGroups` for the log group named in `GetModelInvocationLoggingConfiguration` → `retentionInDays` absent means logs never expire. For an S3 destination, a missing lifecycle expiration rule on the logging prefix (`s3:GetBucketLifecycleConfiguration` → `NoSuchLifecycleConfiguration`, or no rule matching the prefix).

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-COST-006 | Cost Optimization | MEDIUM | Bedrock invocation-log CloudWatch log group has no `retentionInDays`, or the S3 logging prefix has no lifecycle expiration rule — log storage grows without bound. Cite the log group / prefix and its `storedBytes` if available. | Set a retention period: `aws logs put-retention-policy --log-group-name <log-group> --retention-in-days <N>`, or add an S3 lifecycle expiration rule on the prefix. N is `workload-specific` (compliance and debugging need). | https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Working-with-log-groups-and-streams.html |
