# Checks — Evaluation Jobs (LLM-EVAL)

**The LLMOps quality-gate pillar.** Covers Amazon Bedrock model/RAG evaluation jobs and the surrounding automated-evaluation discipline. This is the family that distinguishes LLMOps from generic cloud ops: without evaluation, model/prompt/KB changes ship blind.

Each row: `check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation`

Family code: **EVAL** = evaluation jobs. Family prefix: `LLM-EVAL-`.

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. Thresholds without an AWS-published value are marked `workload-specific` at severity INFO.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-EVAL-001 | Quality & Evaluation | CRITICAL | `ListEvaluationJobs` returns empty (and no custom offline-eval record exists) for a production GenAI workload — no model/RAG quality has ever been measured. Changes to model, prompt, or KB ship with no quality baseline. (First confirm the region supports evaluations — see api-quirks.md.) | Stand up at least one Bedrock evaluation job (`CreateEvaluationJob`) covering the production task, establish a baseline score, and gate future changes on it. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-EVAL-002 | Quality & Evaluation | HIGH | Evaluation is run only manually/ad hoc — no automated pipeline (CodePipeline/Step Functions/EventBridge) triggers an evaluation job on model-version, prompt, or KB change. | Wire evaluation into CI/CD: trigger `CreateEvaluationJob` on each candidate change and publish results before promotion. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-EVAL-003 | Quality & Evaluation | MEDIUM | The newest evaluation dataset (prompt/ground-truth set in S3) is older than 90 days, so evaluation no longer reflects current traffic/content. Threshold **derived** (90d) — adjust per workload. | Refresh the evaluation dataset from recent representative traffic on a schedule; version each dataset in S3. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-datasets.html |
| LLM-EVAL-004 | Quality & Evaluation | MEDIUM | Only automated metrics are used; no human-based evaluation job (`jobType`/human worker flow) for subjective dimensions (helpfulness, tone, safety) where human judgment is required. | Add a human evaluation job (bring-your-own-workforce or managed) for subjective criteria alongside automated metrics. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-human.html |
| LLM-EVAL-005 | Operational Excellence | MEDIUM | Evaluation scores are not emitted to CloudWatch as custom metrics — results sit only in S3, so there is no trend, dashboard, or alarm on quality regressions. | After each eval job, parse the output and `PutMetricData` (e.g., namespace `LLMOps/Evaluation`, dimensions model/version) so quality is trended and alarmable. | https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/publishingMetrics.html |
| LLM-EVAL-006 | Quality & Evaluation | MEDIUM | No A/B / head-to-head model comparison before adopting a new model or version — the candidate is not scored against the incumbent on the same dataset. | Run a comparative evaluation (candidate vs incumbent on the identical dataset and metrics) and decide on the delta. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-create.html |
| LLM-EVAL-007 | Quality & Evaluation | HIGH | No regression gate: a model/prompt/KB/agent change can be promoted even if its evaluation score falls below the established baseline — nothing blocks a quality regression. | Enforce a promotion gate that fails the pipeline when the candidate score drops below baseline by more than an agreed margin. Margin is `workload-specific`. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-EVAL-008 | Operational Excellence | MEDIUM | Evaluation results and datasets are not versioned/retained (overwritten in place, no immutable S3 prefix per run) — past quality can't be reproduced or audited. | Store each eval run's dataset, config, and output under an immutable versioned S3 prefix keyed by run ID + model version. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-output-data.html |
| LLM-EVAL-009 | Quality & Evaluation | MEDIUM | A RAG/KB workload has model evaluation but no retrieval-specific (retrieve / retrieve-and-generate) evaluation — retrieval relevance and grounding are unmeasured. | Add a Bedrock RAG evaluation job measuring retrieval relevance and response grounding (ties to LLM-KB-009). | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html |
| LLM-EVAL-010 | Security/Responsible-AI | MEDIUM | No safety/responsible-AI evaluation dimension (toxicity, harmfulness, robustness/prompt-attack) in the eval set for a customer-facing workload — safety posture is untested beyond the guardrail config itself. | Include safety metrics (toxicity, robustness) in evaluation and track them with the same regression gate (ties to LLM-GRD-007). | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-tasks-metrics.html |
| LLM-EVAL-011 | Operational Excellence | LOW | Latest evaluation job status is `Failed`/`Stopped` and was never re-run — the last known quality signal is a non-result. Threshold `workload-specific`. | Inspect `GetEvaluationJob` failure reason, fix dataset/permissions, and re-run so a valid score exists. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-EVAL-012 | Quality & Evaluation | HIGH | Finish-reason distribution has shifted: the share of invocations ending with `max_tokens` (truncation) rather than `end_turn` (natural completion) has increased by >10 percentage points over the evaluation window compared to the baseline. This is an early, otherwise-invisible indicator of quality regression — outputs are being cut off. Requires model invocation logging enabled (LLM-INV-001) and a metric filter on `stopReason` (LLM-TEL-002). Threshold: >10pp shift is **derived** — adjust per workload. See references/finish-reason-analysis.md. | Investigate: check if `maxTokens` was reduced, if prompt length grew (crowding out output), or if a model version change altered generation length. If the shift correlates with a deployment, roll back or adjust. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html |
| LLM-EVAL-013 | Quality & Evaluation | HIGH | No CloudWatch metric filter exists on the Bedrock invocation log group for `stopReason`, so the finish-reason distribution cannot be trended and the truncation signal is invisible. Requires invocation logging enabled (see llmops-bedrock-configuration for that check). | Create a metric filter `{ $.stopReason = "max_tokens" }` on the invocation log group, publish to a custom namespace, and alarm on a >10pp rise over baseline. See references/finish-reason-analysis.md. | https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html |
| LLM-EVAL-014 | Quality & Evaluation | MEDIUM | Output token counts (`OutputTokenCount`) have risen materially over the window with no corresponding rise in `Invocations` — responses are getting longer, which often precedes a truncation shift and always raises cost. Threshold is `workload-specific`. | Correlate with the finish-reason distribution and prompt changes. If prompts grew, re-check the output budget. See references/finish-reason-analysis.md. | https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-cw.html |
