# Checks — Telemetry Coverage (LLM-TEL)

Covers telemetry coverage verification for GenAI workloads: stage-level observability, finish-reason monitoring, trace-context propagation, structured logging, dashboards, PII masking, custom metric filters, and log retention.

Each row: `check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation`

Family code: **TEL** = telemetry. Family prefix: `LLM-TEL-`.

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. Thresholds without an AWS-published value are marked `workload-specific` at severity INFO.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-TEL-001 | Operational Excellence | CRITICAL | No stage-level telemetry exists across the processing stages (retrieval, inference, tool execution, response generation). Only a single request-boundary latency is measured, so slowness cannot be isolated to a stage. Detect via absence of AgentCore Observability OTLP export, or absence of span-level data in CloudWatch Logs Insights. | Instrument each stage independently — enable AgentCore Observability OTLP spans or emit per-stage spans/log fields — so retrieval, inference, tool execution, and response-generation latency are separately visible. See `checks-agentcore.md` (LLM-AC-005). | https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel08-bp02.html |
| LLM-TEL-002 | Quality & Evaluation | HIGH | No CloudWatch metric filter exists on `stopReason` / `finish_reason` in the Bedrock invocation logs, so a shift in the finish-reason distribution is invisible. A drift from `end_turn` toward `max_tokens` (truncation) is an early, cheap quality-regression indicator — a small check with outsized value. | Create a CloudWatch Logs metric filter extracting `stopReason`/`finish_reason` from invocation logs into a metric, and alarm on a rising `max_tokens` (truncation) share versus baseline. Threshold `workload-specific`. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html |
| LLM-TEL-003 | Operational Excellence | HIGH | Trace-context propagation is not verified across multi-service calls (agent → KB → model → tool). Logs/traces carry no continuous W3C `traceparent` or correlated X-Ray trace IDs spanning the hops, so a single request cannot be followed end-to-end. | Propagate and verify W3C trace-context (or X-Ray trace IDs) through every hop so one trace covers the full agent→KB→model→tool path; confirm with a sampled continuous trace. See `checks-agentcore.md` (LLM-AC-006). | https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel08-bp02.html |
| LLM-TEL-004 | Operational Excellence | MEDIUM | Logs are emitted as unstructured free text rather than structured JSON (Bedrock invocation logs or application logs), hindering query-at-scale in CloudWatch Logs Insights and reliable field extraction. | Emit structured JSON with consistent keys (stage, latency, token counts, model/tool, error, finish-reason); standardize across services so Logs Insights queries and metric filters are reliable. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html |
| LLM-TEL-005 | Operational Excellence | MEDIUM | No CloudWatch dashboard combines the GenAI workload's signals — Bedrock invocation metrics (invocations, latency, 4xx/5xx, throttles, tokens), guardrail metrics, and agent metrics are scattered across consoles with no single operational view. | Build a CloudWatch dashboard that composites Bedrock, guardrail, and agent metrics for the workload so operators have one place to see health and latency. Threshold `workload-specific`. | https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel08-bp02.html |
| LLM-TEL-006 | Security/Responsible-AI | MEDIUM | Invocation-log PII masking is not enabled on a path where sensitive data flows through prompts/completions — raw prompt/response text is delivered to the log destination unmasked. | Enable PII masking/redaction before logging (guardrail sensitive-information `ANONYMIZE`, see LLM-GRD-003) or disable raw text/image data delivery where only metadata is needed, so logs do not retain sensitive content. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html |
| LLM-TEL-007 | Operational Excellence | LOW | No custom metric filters exist beyond the default `AWS/Bedrock` namespace — no per-use-case latency, per-caller token counts, or other workload-specific metrics extracted from logs, limiting operational granularity. Threshold `workload-specific`. | Add CloudWatch Logs metric filters for the dimensions that matter (per-use-case latency, per-caller/per-tenant token counts) so operators can slice beyond the default metrics. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html |
| LLM-TEL-008 | Cost Optimization | INFO | The Bedrock invocation-logging CloudWatch log group has retention set to "Never expire" (`retentionInDays` unset), so log data — including large text/image payloads — accumulates indefinitely and cost grows unbounded. Threshold `workload-specific`. | Set an explicit `retentionInDays` on the log group aligned to compliance/debugging needs; archive to S3 with lifecycle policies if long-term retention is required. | https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Working-with-log-groups-and-streams.html |
