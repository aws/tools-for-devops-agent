# Diagnosis table: symptom → cause → evidence → lookalike

Read this file in Step 3 of every investigation.

## Anchor on the reported symptom and onset

Start with the row for the symptom the operator reported, even if another anomaly looks
bigger. A change that *ended* before the onset (traffic stopping, a load going away) does
not cause symptoms that start after it. Traffic that stops on every node with no errors
and no events means the clients stopped, not that the cache failed. If the window just
before the onset contains a different anomaly, say so, report it separately, and choose
an earlier steady-state window as the baseline.

The cause is confirmed only when its evidence is present **and** the lookalike's evidence
is absent. When a row compares nodes or shards, quote the values for each one; do not
call a node an outlier without the numbers.

## Table

| Symptom | Cause | Discriminating evidence | Lookalike to rule out |
|---|---|---|---|
| Writes fail, `OOM` errors | Memory at maxmemory and nothing evictable: `noeviction`, or a `volatile-*` policy with no keys that have a TTL | Memory at ~100% of maxmemory, **evictions = 0** (quote it), `OOM` error replies (OTel `valkey.errors` with `valkey.error.type="OOM"`), the policy value, and `CurrVolatileItems` (keys with a TTL) | Eviction policy working (evictions > 0, no `OOM`). Fix: if `CurrVolatileItems` is 0, `volatile-lru` frees nothing, so recommend `allkeys-lru` for a pure cache, deleting keys, or more capacity. If one collection keeps growing, trim or expire it first |
| Keys disappear, hit rate drops | Evictions: working set larger than memory | Evictions > 0 and rising while memory sits at max; expirations (`Reclaimed`, OTel `valkey.keys.expired`) flat | TTL expiry (expirations up, evictions 0); cold cache after a failover or node replacement (event, item count drop) |
| Latency up, every shard | Engine saturation | Main-thread CPU at or above the AWS-recommended 90% (`EngineCPUUtilization`, OTel `process.cpu.time` main thread), throughput up, **per-command latency flat** vs baseline; `TrafficManagementActive = 1` | Expensive commands (next row); network allowance exceeded; swap (`SwapUsage`, `MajorPageFaults`) |
| Latency spikes, periodic | Expensive O(N) commands (`KEYS`, `HGETALL`/`SMEMBERS`/`LRANGE` on big keys, `SORT`, scripts) | One command's average latency far above the others; matching slow log entries at the spike times | Saturation (all commands slow together) |
| Latency or CPU on **one shard** | Key-distribution skew: hot key, shared hash tag, or one growing key | One node's throughput or engine CPU well above the other primaries (quote each); the command family that dominates on it names the data type. To find the slot, recommend `CLUSTER SLOT-STATS ORDERBY` (Valkey 8.0+, cluster mode, see engine-followups.md); if the shard's memory also grows while its key count is flat, use `--memkeys`/`--bigkeys` instead; never `MONITOR` on a primary | Undersized node type: all primaries carry similar load. Fix skew with client-side caching or by splitting the key; scaling up or adding shards does not spread one hot key |
| One shard's memory high or climbing | Hash-tag concentration, a big key, or an unbounded collection (a list, set or stream that is never trimmed or expired) in one slot | One primary's memory well above the others (quote each). Memory that grows linearly on one shard while its key count does not (OTel `deriv`/`predict_linear` on `valkey.memory.used`) means one or a few growing keys; project when it reaches maxmemory. To name the key, recommend `--memkeys`/`--bigkeys` on that shard's replica first (engine-followups.md); slot statistics cannot single out one key when all keys share a slot | Uniform memory pressure (all primaries similar) |
| Memory grows faster than key count | Big keys | Bytes per item (`BytesUsedForCache` / `CurrItems`) rising; `NetworkBytesOut` spikes on one node with engine CPU; slow log shows `HGETALL`/`LRANGE`/`SMEMBERS`. To name the key, recommend `--memkeys`/`--bigkeys` on a replica | Many small keys: bytes per item flat |
| Command timeouts, cluster looks healthy | Client command or socket timeout too tight for the full round trip | Engine CPU low, connections steady, no errors, server latency (`SuccessfulReadRequestLatency`/`SuccessfulWriteRequestLatency` p99 and maximum) normal. These metrics measure the engine's response time only: the client also pays the network round trip, its own processing and per-command TLS encryption, which no ElastiCache metric shows. The TLS handshake is paid only when a connection is opened, so it matters only with connection churn. Compare the client's timeout with its own observed round trip (p99 and maximum); if either is unknown, report it as the key missing fact and ask for it. Note the client and node AZs from the deployment details. State the client's location and any per-shard or per-AZ effect as a hypothesis unless per-shard client measurements exist; with several clients, or clients outside the account, say the client cannot be located | Connection churn (new connections high); engine saturation (CPU high); network allowance exceeded. Fix: raise the timeout to a safe multiple of the client's observed maximum round trip. Do not recommend a bigger node |
| Timeouts in bursts that get worse | Retries without backoff amplifying a brief stall | Short bursts where command rate and new connections jump far above the steady level right after a small latency or CPU blip, then repeat; the user-facing request rate did not change | Steady connection churn (no bursts); a real traffic increase (application requests rose too). Fix: exponential backoff with jitter, a retry cap, a circuit breaker |
| Latency up, engine CPU low | Network limit on the node, or requests queuing in a too-small client pool | Network allowance exceeded > 0 (`NetworkBandwidthIn/OutAllowanceExceeded`, `NetworkPacketsPerSecondAllowanceExceeded`, `NetworkConntrackAllowanceExceeded`; OTel `system.network.allowance_exceeded` by reason), `NetworkBaselineUsage*Percentage` above 100 (burst credits in use), or p99 network rate near `system.network.bandwidth.limit`. If network is clean too, the queue is in the client | Engine saturation (CPU high); expensive commands. Fix for network: larger or network-optimized node type, spread traffic across shards, smaller payloads |
| Current connections climb steadily | Connection leak or unbounded client pool | `CurrConnections` (OTel `valkey.clients.connected`) rising for hours without a matching rise in commands; later `maxclients` and rejected connections | Real traffic growth (commands grow in proportion). Fix: bound the pool, close connections, set the `timeout` parameter (seconds, 0 = never; values from 20) to close idle clients |
| Connection errors or timeouts | `maxclients` reached | Connected clients near the limit (65,000 on most node types; 20,000 on `t3.micro`/`t4g.micro`, 46,000 on `t3.small`/`t3.medium`; OTel `valkey.clients.max`), `RejectedConnections` > 0 | Connection churn |
| Connection timeouts, CPU up | Connection churn: no pooling, a new TLS connection per request | New connections per second very high (`NewConnections`; OTel `rate(valkey.connections.received)`) while current connections stay flat; handshake commands (`HELLO`, `CLIENT SETINFO`, `AUTH`, `PING`) at a high rate with no data commands; no rejections | `maxclients` (rejections > 0); security group change (CloudTrail, connections drop to 0) |
| Stale reads from replicas | Replication lag | `ReplicationLag` (seconds) up on replicas. Cause: a snapshot or sync (`SaveInProgress`, snapshot event), a write burst on the primary (`ReplicationBytes` up), or a broken link (OTel `valkey.replication.link_healthy = 0` on the replica) | Application reading through a cache layer with its own TTL |
| Brief outage, then errors | Failover or maintenance | Failover/replacement event at the onset; node role flip (`IsMaster`, OTel `valkey.replication.is_primary`). If errors persist **after** failover completes, the client is the cause: cached DNS, a pinned node endpoint, or a cluster client without topology refresh | Network or client-side failure (no event, no role change) |
| Authentication errors, often at regular intervals | IAM auth token expired, or ElastiCache disconnecting an IAM-authenticated connection after 12 hours | `IamAuthenticationExpirations` > 0, `AuthenticationFailures` rising (OTel `valkey.acl.denied` with reason `auth`); failures repeat about every 12 hours of connection age, or appear when a client re-authenticates with a token older than 15 minutes | Wrong password or user (failures constant from the start, no expirations); missing `elasticache:Connect` permission; `IamAuthenticationThrottling` > 0. Fix: generate a fresh token for every new connection, and re-authenticate with `AUTH`/`HELLO` and a fresh token before 12 hours |
| Clients cannot connect after a change, no engine errors | In-transit encryption mismatch between client and cache | `TransitEncryptionEnabled`/`TransitEncryptionMode` on the cache versus the client's TLS setting; a CloudTrail `ModifyReplicationGroup` that set `TransitEncryptionMode` to `required` at the onset (it drops unencrypted connections); connections from that client drop to 0 while the cache is healthy | Security group change (CloudTrail on the group); failover (event). Fix: enable TLS in the client, or move through `preferred` before `required` |
| Serverless commands throttled | ECPU usage limit reached | `ThrottledCmds` > 0 while `ElastiCacheProcessingUnits` sits at `CacheUsageLimits.ECPUPerSecond.Maximum` | Workload ramping faster than serverless scales (no maximum reached, throttling during a fast ramp; pre-scale with a minimum ECPU limit); one hot slot above its 30,000 ECPU/s limit (90,000 with read from replica) |
| A specific engine error reply | Read [error-strings.md](error-strings.md) | | |

## Stop conditions

- Engine CPU well below the 90% threshold and connections stable: the cause is not
  engine capacity or connections. Look at commands, the slow log and the client.
- Evictions 0 and memory well below maxmemory: eviction is not the cause.
