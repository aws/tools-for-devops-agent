# Checks — Evaluation (LLM-EVAL-*, LLM-SM-EVAL-*)

**The OpsAI quality-gate pillar.** Covers Amazon Bedrock model/RAG evaluation jobs and the surrounding automated-evaluation discipline, plus SageMaker-side evaluation / benchmark jobs for a customized GenAI model. This is the family that distinguishes OpsAI from generic cloud ops: without evaluation, model/prompt/KB changes ship blind.

Each row: `check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation`

Family codes: **EVAL** = Bedrock evaluation jobs and quality signals, prefix `LLM-EVAL-`; **SM-EVAL** = SageMaker-side evaluation, prefix `LLM-SM-EVAL-`.

## Bedrock evaluation (LLM-EVAL-*)

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. Thresholds without an AWS-published value are marked `workload-specific` at severity INFO.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-EVAL-001 | Quality & Evaluation | CRITICAL | `ListEvaluationJobs` returns empty (and no custom offline-eval record exists) for a production GenAI workload — no model/RAG quality has ever been measured. Changes to model, prompt, or KB ship with no quality baseline. (First confirm the region supports evaluations — see api-quirks.md.) | Stand up at least one Bedrock evaluation job (`CreateEvaluationJob`) covering the production task, establish a baseline score, and gate future changes on it. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-EVAL-002 | Quality & Evaluation | HIGH | Evaluation is run only manually/ad hoc — no automated pipeline (CodePipeline/Step Functions/EventBridge) triggers an evaluation job on model-version, prompt, or KB change. | Wire evaluation into CI/CD: trigger `CreateEvaluationJob` on each candidate change and publish results before promotion. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-EVAL-003 | Quality & Evaluation | MEDIUM | The newest evaluation dataset (prompt/ground-truth set in S3) is older than 90 days, so evaluation no longer reflects current traffic/content. Threshold **derived** (90d) — adjust per workload. | Refresh the evaluation dataset from recent representative traffic on a schedule; version each dataset in S3. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-evaluation-prompt-datasets.html |
| LLM-EVAL-004 | Quality & Evaluation | MEDIUM | Only automated metrics are used; no human-based evaluation job (`jobType`/human worker flow) for subjective dimensions (helpfulness, tone, safety) where human judgment is required. | Add a human evaluation job (bring-your-own-workforce or managed) for subjective criteria alongside automated metrics. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-human.html |
| LLM-EVAL-005 | Operational Excellence | MEDIUM | Evaluation scores are not emitted to CloudWatch as custom metrics — results sit only in S3, so there is no trend, dashboard, or alarm on quality regressions. | After each eval job, parse the output and `PutMetricData` (e.g., namespace `OpsAI/Evaluation`, dimensions model/version) so quality is trended and alarmable. | https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/publishingMetrics.html |
| LLM-EVAL-006 | Quality & Evaluation | MEDIUM | No A/B / head-to-head model comparison before adopting a new model or version — the candidate is not scored against the incumbent on the same dataset. | Run a comparative evaluation (candidate vs incumbent on the identical dataset and metrics) and decide on the delta. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-evaluation-jobs-management-create.html |
| LLM-EVAL-007 | Quality & Evaluation | HIGH | No regression gate: a model/prompt/KB/agent change can be promoted even if its evaluation score falls below the established baseline — nothing blocks a quality regression. | Enforce a promotion gate that fails the pipeline when the candidate score drops below baseline by more than an agreed margin. Margin is `workload-specific`. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-EVAL-008 | Operational Excellence | MEDIUM | Evaluation results and datasets are not versioned/retained (overwritten in place, no immutable S3 prefix per run) — past quality can't be reproduced or audited. | Store each eval run's dataset, config, and output under an immutable versioned S3 prefix keyed by run ID + model version. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-evaluation-report-s3.html |
| LLM-EVAL-009 | Quality & Evaluation | MEDIUM | A RAG/KB workload has model evaluation but no retrieval-specific (retrieve / retrieve-and-generate) evaluation — retrieval relevance and grounding are unmeasured. | Add a Bedrock RAG evaluation job measuring retrieval relevance and response grounding (the Knowledge Bases / RAG area checks whether such a job covers each KB). | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html |
| LLM-EVAL-010 | Security/Responsible-AI | MEDIUM | No safety/responsible-AI evaluation dimension (toxicity, harmfulness, robustness/prompt-attack) in the eval set for a customer-facing workload — safety posture is untested beyond the guardrail config itself. | Include safety metrics (toxicity, robustness) in evaluation and track them with the same regression gate (ties to the Bedrock Guardrails area). | https://docs.aws.amazon.com/bedrock/latest/userguide/model-evaluation-tasks.html |
| LLM-EVAL-011 | Operational Excellence | LOW | Latest evaluation job status is `Failed`/`Stopped` and was never re-run — the last known quality signal is a non-result. Threshold `workload-specific`. | Inspect `GetEvaluationJob` failure reason, fix dataset/permissions, and re-run so a valid score exists. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-EVAL-012 | Quality & Evaluation | HIGH | Finish-reason distribution has shifted: the share of invocations ending with `max_tokens` (truncation) rather than `end_turn` (natural completion) has increased by >10 percentage points over the evaluation window compared to the baseline. This is an early, otherwise-invisible indicator of quality regression — outputs are being cut off. Requires model invocation logging enabled (Bedrock invocation-logging area) and a metric filter on `stopReason` (LLM-EVAL-013). Threshold: >10pp shift is **derived** — adjust per workload. See references/finish-reason-analysis.md. | Investigate: check if `maxTokens` was reduced, if prompt length grew (crowding out output), or if a model version change altered generation length. If the shift correlates with a deployment, roll back or adjust. | https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html |
| LLM-EVAL-013 | Quality & Evaluation | HIGH | No CloudWatch metric filter on the Bedrock invocation log group references `output.outputBodyJson.stopReason`, so the finish-reason distribution cannot be trended and the truncation signal is invisible. A filter on a top-level `stopReason` field (not under `output.outputBodyJson`) never matches; report it under this check as present but never matching. Requires invocation logging enabled (a Bedrock invocation-logging area check). | Create a metric filter `{ $.output.outputBodyJson.stopReason = "max_tokens" }` on the invocation log group, publish to a custom namespace, and alarm on a >10pp rise over baseline. See references/finish-reason-analysis.md. | https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html |
| LLM-EVAL-014 | Quality & Evaluation | MEDIUM | Output token counts (`OutputTokenCount`) have risen materially over the window with no corresponding rise in `Invocations` — responses are getting longer, which often precedes a truncation shift and always raises cost. Threshold is `workload-specific`. | Correlate with the finish-reason distribution and prompt changes. If prompts grew, re-check the output budget. See references/finish-reason-analysis.md. | https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html |

## SageMaker-side evaluation / benchmark jobs (LLM-SM-EVAL-*)

Covers Amazon SageMaker-side evaluation / benchmark jobs for a customized GenAI / LLM model — Nova eval recipes and LLM-as-judge jobs run as a SageMaker job.

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. A *tuning or right-sizing judgment* with no AWS-published number is marked `workload-specific` at severity INFO; a *binary present/absent/failed* state (a job FAILED, no checkpoint produced, access denied) keeps its catalog severity even when AWS publishes no number.

SageMaker-side model evaluation for customized LLMs (Nova eval recipes, LLM-as-judge run as a SageMaker job). LLM-SM-EVAL-004 marks a request that is actually Bedrock-native; it is then diagnosed on the Bedrock path with LLM-EVAL-* ids.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-SM-EVAL-001 | Quality & Evaluation | MEDIUM | A customized/fine-tuned LLM artifact (from a SageMaker training or customization job) was registered or deployed with **no** SageMaker-side evaluation run against it — quality/regression is unmeasured before serving. Threshold `workload-specific`. | Run a SageMaker model-evaluation / Nova eval recipe (or LLM-as-judge job) against a held-out set before promoting the customized model; gate promotion on the result. | https://docs.aws.amazon.com/nova/latest/userguide/customize-fine-tune-evaluate-recipe-examples.html |
| LLM-SM-EVAL-002 | Reliability | HIGH | A SageMaker evaluation/benchmark job `Failed` — read the `FailureReason` for a bad eval-dataset S3 path, a malformed eval recipe, or a judge-model access/permission error. | Fix the indicated cause (dataset path, recipe schema, or judge-model IAM/access) and resubmit the evaluation job; validate the eval dataset format first. | https://docs.aws.amazon.com/nova/latest/userguide/customize-fine-tune-evaluate-recipe-examples.html |
| LLM-SM-EVAL-003 | Operational Excellence | LOW | Evaluation output exists but is not published as a tracked metric / not retained for run-over-run comparison — no quality trend for the customized model. Threshold `workload-specific`. | Publish eval scores as custom CloudWatch metrics (namespace `OpsAI/Evaluation`) and retain the output prefix so regressions are visible over time. | https://docs.aws.amazon.com/sagemaker/latest/dg/monitoring-cloudwatch.html |
| LLM-SM-EVAL-004 | Quality & Evaluation | INFO | The evaluation request is actually **Bedrock-native** (a Bedrock `CreateEvaluationJob`, not a SageMaker job) — not a SageMaker-side job. | Diagnose it on this skill's Bedrock evaluation path with LLM-EVAL-* ids; do not assign LLM-SM-EVAL ids to it. This row is a routing marker, not a defect in the SageMaker workload, so its citation is the Bedrock-native evaluation doc because the request belongs to that service. | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
