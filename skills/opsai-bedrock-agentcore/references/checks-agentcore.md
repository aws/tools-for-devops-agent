# Checks — Bedrock AgentCore (LLM-AC)

Covers Amazon Bedrock AgentCore: runtime execution role, gateway configuration, VPC connectivity, stage-level telemetry/observability, runtime/gateway/memory quotas and session limits (LLM-AC-011), cross-account access through resource-based policies (LLM-AC-014), AgentCore Memory: short-term events, branches, asynchronous long-term extraction and Memory latency (LLM-AC-012), and Browser / Code Interpreter sessions plus console pages that do not load in the operator's own browser (LLM-AC-013).

Each row: `check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation`

Family code: **AC** = AgentCore. Family prefix: `LLM-AC-`.

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. Thresholds without an AWS-published value are marked `workload-specific` at severity INFO.

The agent cannot invoke models or read its dependencies. | Grant the runtime role least-privilege permissions for every action it exercises (model invoke on the specific model/inference-profile ARNs, S3 read on the source bucket, CloudWatch Logs write, gateway target actions); re-simulate until all required actions are `allowed`. | https://docs.aws.amazon.com/bedrock/latest/userguide/agentcore.html |

| LLM-AC-011 | Reliability/Performance | HIGH | A runtime, gateway or memory call is throttled (HTTP 429 / `ThrottlingException`) or slows under concurrency. First establish **which layer throttled**: (a) `InvokeAgentRuntime` itself returned 429 and the runtime log group has no line for that request, so the platform rejected it before the container ran: compare the aggregate rate with the account's AgentCore data-plane quota (1,000 TPS shared by `InvokeAgentRuntime` and the other data-plane APIs) and, when each call or test worker uses a fresh `runtimeSessionId`, with the **new session creation rate (25 TPS per account, shared across all endpoints)**; (b) the agent code's own `bedrock-runtime` `InvokeModel`/`Converse` call is throttled inside the container (the runtime log shows the model exception): that is the Bedrock model quota for that model, not an AgentCore quota; (c) gateway `tools/call`/`tools/list` above 200 TPS per gateway or per account; (d) AgentCore Memory `CreateEvent` above 5 TPS per actor per session (with conversational payloads). Separately, concurrent requests sent to **one session** share that Runtime session's fixed hardware allocation (2 vCPU / 8 GB, not adjustable; Browser sessions have 1 vCPU / 4 GB, see LLM-AC-013; up to 250 concurrent connections per session on platform V2), so throughput falls as they contend. AWS documents no per-session network bandwidth quota; do not claim one. For a cross-account invocation the calls count against the quotas of the account that owns the runtime. | Name the layer and the quota with its documented value. For (a): stagger or rate-limit callers below the quota, reuse a stable session ID per user or conversation instead of a new one per call, add client retry with exponential backoff and jitter, and request a Service Quotas increase for the adjustable quota if sustained load needs it (the quota owner is the runtime's account). For (b): request a Bedrock model quota increase for that model and spread load with a cross-Region inference profile. For (c)/(d): request the gateway quota increase or batch memory events. For same-session contention: send concurrent work to separate sessions (or use a larger compute type, accepting its longer start-up); network or VPC changes do not fix it. Retries or longer timeouts alone are not a fix. Report a 403 seen at the same time as a separate permission finding (LLM-AC-001/002). | https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html |
| LLM-AC-012 | Reliability | HIGH | An agent that uses (or should use) **AgentCore Memory** loses context, reads the wrong history, gets unexpected branch or long-term results, or Memory calls are slow or failing. Establish which part of Memory is involved before naming a cause: (a) **short-term memory** is only what the agent code writes with `CreateEvent` and reads back with `ListEvents`/`GetEvent`, scoped by `memoryId` + `actorId` + `sessionId`; a runtime session ID routes calls to a microVM and stores nothing, so if the code never writes and reads events per turn there is no conversation history to lose. In a multi-agent system, agents see the same context only if they write to and read from the same memory resource with the same actor/session scoping; (b) **branches** are created by `CreateEvent` with `branch` (`name`, `rootEventId`) for edits or alternative paths, and events are read per branch; the data-plane API has no branch merge or sync operation, so events written to one branch after the fork do not appear in another; (c) **long-term memory** is extracted and consolidated **asynchronously in the background** by the memory's strategies after `CreateEvent` or `IngestData`, stored as memory records under each strategy's namespace and read with `RetrieveMemoryRecords` (semantic search) or `ListMemoryRecords`; records are not available immediately, blob payloads are never extracted, and a missing or invalid `extractionConfig` namespace variable still stores the event but may skip extraction (visible only in the memory's vended logs); (d) **slow or failing Memory calls**: read the Memory CloudWatch metrics (`CreateEvent`/`RetrieveMemoryRecords` `Invocations`, `Latency`, `Errors`, and ingestion metrics per memory) over the window; `CreateEvent` throttling is the 5 TPS per actor per session quota (LLM-AC-011). Threshold `workload-specific`. | Name the part (a)-(d) and the observed evidence. (a) Make the agent write each turn with `CreateEvent` and load history with `ListEvents` on every invoke; for agents that must share context, use one shared memory resource with consistent `actorId`/`sessionId` scoping across all of them. (b) Reconcile branches in the application (re-branch from the edited event with a new `rootEventId`, or re-run the affected step); do not promise an automatic merge, and it is not a bug for Support to fix. (c) Wait for asynchronous extraction before reading records, check the strategy namespaces and `extractionConfig`, and enable log delivery to see extraction errors. (d) If Memory latency rose with no change on the customer side (deployments, errors, throttles and traffic ruled out), report it as a likely service-side regression without naming an internal cause (capacity, deployment) AWS has not confirmed, and prepare a support case with the memory ID, Region, onset time, request IDs with timestamps, the metric window and the application logs. Do not re-list a cause the operator has already verified (for example a session ID they confirmed is stable). | https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-types.html ; https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/short-term-create-event.html ; https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-observability.html |
| LLM-AC-013 | Reliability | MEDIUM | An AgentCore **Browser** or **Code Interpreter** session crashes, slows, renders at the wrong size or ends early, or a page the operator opens in **their own web browser** (the AgentCore or CloudWatch console, an observability dashboard) stays loading or does not render. First establish **which browser is involved**. (a) **The managed Browser tool:** each session has a fixed hardware configuration of 1 vCPU / 4 GB (not adjustable; Code Interpreter sessions 2 vCPU / 8 GB; the Runtime figures in LLM-AC-011 do not apply), 10 GB disk, one automation stream and one live view stream, and a timeout set at `StartBrowserSession` (`sessionTimeoutSeconds`, maximum 8 hours); the viewport is set per session with `viewPort`. When recording is enabled, the session also captures DOM changes, network traffic and console logs to S3. A crash or shrink that appears only after many tasks in one long session points at state the session accumulates (tabs, DOM, downloads, recording), but AWS documents no internal crash mechanism: state resource exhaustion as a hypothesis with the tests that separate it, never as a confirmed memory limit or kernel cause. Do not attribute a viewport change to a specific mechanism you did not observe. (b) **The operator's own browser:** a console page that loads in one browser, a private window or for a colleague but not in this browser is client-side until shown otherwise (cache, extensions, corporate proxy, VPN, TLS inspection or certificates, DNS). | (a) Recycle sessions: `StopBrowserSession` and start a fresh session after a fixed number of tasks or a fixed age instead of one long session (for example log out and back in on the new session); close tabs and clear downloads between tasks; if recording is enabled, run the same workload with a browser that has recording disabled and keep recording only where it is needed; set `viewPort` explicitly on every session and re-check it after a navigation that changes it. If the failure reproduces on fresh, short sessions, open an AWS Support case with the browser ID, session IDs, Region, timestamps, the console logs or recording, and say the internal cause is unconfirmed. (b) Before naming a service or console fault: try a private window and a second browser, clear the cache, disable extensions, capture the failed requests in the developer tools Network tab (a HAR file), and ask the IT or network team to check proxy, VPN, certificate and DNS settings; raise a support case with the HAR only if a clean browser on another network also fails. | https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html ; https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-resource-session-management.html ; https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-session-recording.html |
| LLM-AC-014 | Security/Reliability | HIGH | A principal in **another account** calls an AgentCore Runtime, Gateway or Memory resource and the call is denied, or appears to do nothing. Access needs an allow for **that exact action** from the caller's identity policy (in the caller's account) **and** from the resource-based policy on the resource (`bedrock-agentcore-control get-resource-policy`); for a cross-account principal a missing allow on either side denies the call, and an explicit deny anywhere wins. For `InvokeAgentRuntime` both the runtime and the endpoint (DEFAULT or named) need a resource-based policy that allows the principal. Each action is granted separately: an allow for `InvokeAgentRuntime` does not cover `StopRuntimeSession`, `InvokeAgentRuntimeCommand`, `InvokeGateway` or the Memory actions (`CreateEvent`, `ListEvents`, `RetrieveMemoryRecords`). A session the caller fails to stop stays active until its idle timeout (15 min default) and counts toward the runtime owner's active-session quota, so a denied `StopRuntimeSession` that the client code ignores shows up later as 429s (LLM-AC-011). An S3 bucket in another account is api-quirks §15. Threshold: any denied required action. | Name the missing action and the side it is missing on, then add it: the action on the runtime and endpoint ARNs in the caller's identity policy, and the same action for that principal in the resource-based policy (`put-resource-policy`; `Resource` must be the exact ARN of the resource the policy is attached to, `*` is rejected; OAuth-authenticated resources use `"Principal": "*"` with conditions). Make the client log and alarm on a failed stop instead of swallowing it, and add an application-side metric of open sessions so accumulation is seen before the quota. A quota increase or a shorter idle timeout alone does not fix it. | https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/resource-based-policies.html |
