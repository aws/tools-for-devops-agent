# Checks — Agents & Action Groups (LLM-AGT)

Covers Amazon Bedrock Agents Classic (maintenance mode), action groups, prompt management, and tracing. LLM-AGT-011 is the migration advisory.

Each row: `check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation`

Family code: **AGT** = agents and action groups. Family prefix: `LLM-AGT-`.

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. Thresholds without an AWS-published value are marked `workload-specific` at severity INFO.

| check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation |
|---|---|---|---|---|---|
| LLM-AGT-001 | Security/Responsible-AI | CRITICAL | `GetAgent` shows no `guardrailConfiguration` (no `guardrailIdentifier`/`guardrailVersion`) on a production agent — user input and agent output are unfiltered. | Attach a published guardrail version to the agent and re-prepare (`PrepareAgent`); verify blocked inputs are rejected. | https://docs.aws.amazon.com/bedrock/latest/userguide/agents-guardrail.html |
| LLM-AGT-002 | Security | HIGH | An action group's Lambda execution role grants broad permissions (`Resource: "*"`, wildcard services, or `AdministratorAccess`) — a prompt-driven tool call can reach far beyond its intended scope. | Scope each action-group Lambda role to least privilege (specific actions + resource ARNs); the agent should only reach what the tool legitimately needs. | https://docs.aws.amazon.com/bedrock/latest/userguide/agents-action-create.html |
| LLM-AGT-003 | Operational Excellence | MEDIUM | Agent uses inline/base prompts edited in place with no Prompt Management versioning, or references prompt by `DRAFT` — prompt changes are untracked and not promotable through a controlled flow. | Store the agent's prompt templates in Bedrock Prompt Management with published versions; reference pinned versions. | https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management.html |
| LLM-AGT-004 | Cost Optimization | LOW | Agent/alias has had zero `InvokeAgent` activity over a sustained window (no `AWS/Bedrock/Agents` invocation metric data, no invocation logs) — idle/abandoned agent still provisioned. | Confirm with the owner and decommission unused agents/aliases, or document why they are retained. Threshold `workload-specific`. | https://docs.aws.amazon.com/bedrock/latest/userguide/agents-view.html |
| LLM-AGT-005 | Operational Excellence | HIGH | Agent is invoked in production with `enableTrace` never used / traces not captured, so there is no record of orchestration reasoning, tool calls, or KB lookups for debugging. | Enable trace on `InvokeAgent` for diagnostic paths and persist traces (log them) for troubleshooting and audit. | https://docs.aws.amazon.com/bedrock/latest/userguide/agents-test.html |
| LLM-AGT-006 | Security | HIGH | Code Interpreter is enabled on the agent but surrounding controls are weak — no session isolation review, no output handling controls, broad downstream permissions. | Keep Code Interpreter in its managed sandbox, restrict what generated code can reach via the agent's role, and review session data handling. | https://docs.aws.amazon.com/bedrock/latest/userguide/agents-code-interpretation.html |
| LLM-AGT-007 | Operational Excellence | MEDIUM | Application invokes the agent's `DRAFT`/`TSTALIASID` test alias in production instead of a published numbered version alias — behavior changes whenever the draft is edited. | Create a published agent version and a production alias; point applications at the stable alias. | https://docs.aws.amazon.com/bedrock/latest/userguide/deploy-agent.html |
| LLM-AGT-008 | Reliability | MEDIUM | Agent `foundationModel` is a direct model ID with no cross-region inference profile and no fallback; agent throttles/fails under regional capacity pressure. | Configure the agent's model as a cross-region inference profile where supported (see LLM-INV-002). | https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html |
| LLM-AGT-009 | Operational Excellence | LOW | Memory / session TTL (`memoryConfiguration`) left default where longer or shorter retention is required by the use case, or session state not cleared for multi-tenant use. Threshold `workload-specific`. | Set `memoryConfiguration` (enabled types, `storageDays`) to match data-retention and multi-tenant isolation requirements. | https://docs.aws.amazon.com/bedrock/latest/userguide/agents-memory.html |
| LLM-AGT-010 | Quality & Evaluation | MEDIUM | No regression evaluation of the agent (end-to-end task success / tool-selection accuracy) before promoting a new agent version — quality change is unmeasured. | Run an agent/end-to-end evaluation against a fixed task set before promoting each version (see LLM-EVAL-007). | https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html |
| LLM-AGT-011 | Operational Excellence | LOW | **New, advisory.** The workload runs Amazon Bedrock Agents Classic, which is in maintenance mode: it is no longer open to new customers from July 30, 2026, and for existing customers it remains available with no planned end-of-life date but "no new features are planned". A still-working Classic agent is not a reason to skip this. Advisory, not an outage: raise at INFO when purely informational, LOW when a migration should be planned. | Plan migration to AgentCore via the **AgentCore harness** (config-based, closest analog to Classic) or **code-defined agents on AgentCore**; AWS ships a migration skill in the agent toolkit for AWS (prompt: "Help me migrate my Bedrock Agent to AgentCore harness"). Knowledge Bases are unaffected; model-level guardrails still apply through AgentCore, with agent-level enforcement via gateway policies. | https://docs.aws.amazon.com/bedrock/latest/userguide/agents-classic-maintenance-mode.html |
