# Checks — Guardrails (LLM-GRD)

Covers Amazon Bedrock Guardrails (responsible-AI controls).

Each row: `check-id | pillar | severity | detection-rule | remediation | AWS-doc-citation`

Family code: **GRD** = guardrails. Family prefix: `LLM-GRD-`. Ids in use: LLM-GRD-001..011 and LLM-GRD-021.

Severity scale: CRITICAL > HIGH > MEDIUM > LOW > INFO. Thresholds without an AWS-published value are marked `workload-specific` at severity INFO.

Every policy check below reads the **version the production path enforces** (resolved with the table in `guardrails-collection-reference.md`, Guardrails section), never an unpinned DRAFT. "Configured" means the element is present **and** its action is `BLOCK` (`ANONYMIZE` is acceptable for PII) **and** evaluation is enabled on the side the path uses; an element with action `NONE` is detect mode (the trace returns the detection) and an element with evaluation disabled on a side is not evaluated there; both leave that side unprotected and are LLM-GRD-011, whatever the strength. Field names are those of the `GetGuardrail` response: content, PII, regex, topic and word elements carry `inputAction`/`outputAction` and `inputEnabled`/`outputEnabled` (a PII entity or regex can return only `action`: `guardrails-api-quirks.md` §17); contextual grounding filters carry `action`/`enabled`.

| LLM-GRD-001 | Security/Responsible-AI | CRITICAL | A customer-facing / production model invocation path (agent alias, flow node, app `InvokeModel`/`Converse`, `RetrieveAndGenerate`) applies no guardrail: the resolution table in `guardrails-collection-reference.md` finds no request-level guardrail for the path **and** Step 1a found no account-level enforcement (`ListEnforcedGuardrailsConfiguration` empty in the Region) **and** no organization-level enforcement (`DescribeEffectivePolicy` with `PolicyType` `BEDROCK_POLICY` returns none). Not raised while either enforcement exists — evaluate the enforced version instead (LLM-GRD-021 records the enforcement state). An enforcement read that fails (`AWSOrganizationsNotInUseException`, AccessDenied) is a disclosed gap, never "no enforcement". Trace evidence, when present: `appliedGuardrailDetails.guardrailOrigin` = `REQUEST` \| `ACCOUNT_ENFORCED` \| `ORGANIZATION_ENFORCED`. `ListGuardrails` may even be empty. | Create a guardrail with `CreateGuardrail`, publish a numeric version, and attach it to every production invocation path (agent, flow node, request `guardrailConfig`) or enforce it account-wide with `PutEnforcedGuardrailConfiguration`; verify with the `AWS/Bedrock/Guardrails` `Invocations` metric for that version. | https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html · https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-enforcements.html |
| LLM-GRD-002 | Security/Responsible-AI | HIGH | On the enforced version, `contentPolicy` is absent, or a harmful-content filter (`type` `HATE`, `INSULTS`, `SEXUAL`, `VIOLENCE`, `MISCONDUCT`) has `inputStrength`/`outputStrength` `NONE`, `inputAction`/`outputAction` not `BLOCK`, or `inputEnabled`/`outputEnabled` false on a side the path uses. `PROMPT_ATTACK` is evaluated on input only: the gap is `inputStrength` below `MEDIUM` or `inputAction` not `BLOCK`; its output side is not applicable and is never a finding. | Configure the five harmful-content filters at `MEDIUM`/`HIGH` strength with action `BLOCK` and evaluation enabled on both input (prompt) and output (response); configure `PROMPT_ATTACK` on input only at `MEDIUM`/`HIGH` with `inputAction` `BLOCK`. On `InvokeModel`/`InvokeModelWithResponseStream` paths the prompt-attack filter evaluates only user input wrapped in `amazon-bedrock-guardrails-guardContent_*` input tags (AWS: without tags, prompt attacks for those use cases are not filtered) — confirm the application tags user input, or use `Converse`. | https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-content-filters.html · https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-prompt-attack.html |
| LLM-GRD-003 | Security/Responsible-AI | HIGH | `sensitiveInformationPolicy` absent, or no `piiEntities` / `regexes` entry has `inputAction`/`outputAction` `BLOCK` or `ANONYMIZE` with `inputEnabled`/`outputEnabled` true on the sides the path needs (an entry whose action is `NONE` is detect mode, LLM-GRD-011; an `ANONYMIZE` entry that returns only `action`, with no `inputAction`/`outputAction`, was masked on output and not on input in a test, so its input coverage is unproven (raise this check for the input side when the path needs it), and for an untested `action`-only `BLOCK` entry report the input side as could not confirm, a disclosed gap and not a finding: `guardrails-api-quirks.md` §17). | LLM-GRD-004 | Security/Responsible-AI | MEDIUM | `topicPolicy` is absent or has an empty `topics` list, or every topic has `inputAction`/`outputAction` `NONE` or `inputEnabled`/`outputEnabled` false on the sides the path uses — no denied topic is enforced for a domain where off-topic / disallowed subjects are a known risk. | Define denied topics with clear definitions and sample phrases, action `BLOCK`, evaluation enabled on input and output. | LLM-GRD-010 | Security/Responsible-AI | MEDIUM | `GetGuardrail` returns no `kmsKeyArn` (the guardrail is encrypted with an AWS managed key), or `kms:DescribeKey` on that ARN returns `KeyMetadata.KeyManager` `AWS` rather than `CUSTOMER`, where policy requires CMK encryption of the guardrail configuration. | Create a customer managed KMS key and associate it with the guardrail when creating or updating it; confirm `kmsKeyArn` on the enforced version points at a `CUSTOMER`-managed key. | https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-permissions-kms.html |
| LLM-GRD-011 | Security/Responsible-AI | HIGH | Any policy element on the enforced version has `inputAction`/`outputAction` = `NONE` or `inputEnabled`/`outputEnabled` = false (contextual grounding filters: `action` `NONE` or `enabled` false) on a side the production path uses — with action `NONE` (detect mode) the guardrail returns detection information in the trace but blocks or masks nothing, and with evaluation disabled the side is not evaluated at all (AWS: the evaluation does not appear in the response); either way that side is unprotected, whatever the strength. | LLM-GRD-021 | Security/Responsible-AI | INFO | `workload-specific`.
